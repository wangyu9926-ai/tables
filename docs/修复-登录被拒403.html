登录提示「请求不是本站页面发起的，已拒绝」

按顺序做：第 0 步先让你能用 → 第 1 步查是哪种前端 → 第 2 步三种修法选一个 → 第 3 步验证。全程约 10 分钟。

不是登录失败账号密码没被校验，请求在门口就被挡了
应用是好的同条件下换一种请求方式返回 401（正常）
原因一句话代理把「地址」改了，应用认不出来是自己人

原理为什么会有这道检查

浏览器每次「写」操作会带一个「我从哪个页面来」的标记。应用要确认：这个请求确实是我们自己的页面发的，不是别的网站借你的登录状态偷偷发的（这叫 CSRF 防护）。

浏览器
页面在 http://data.sentuor.com
→
代理 / 反向代理
转发时把地址改成 127.0.0.1:8614
→
应用
看到的地址对不上 → 拒绝

所以只要让代理把原始地址（Host 头）原样传进来，或者临时放宽这道检查，就能登录。

第 0 步先让你今天能干活（1 分钟，不用改任何配置）

用最新版 Chrome 或 Edge打开同一个地址再登录。

如果能登录：说明应用完全正常，只是你之前用的浏览器内核比较老（不发送那个「来源标记」，应用就走了备用判断，而备用判断正好被代理改坏了）。先这样干活，下面的第 2 步修完，所有浏览器都能用。
如果 Chrome 也报同样的红字：直接跳到第 2 步的「情况 B」。

第 1 步确认域名后面挂的是什么（一条命令）

在 PowerShell 里执行（把域名换成你的，注意是 http）：

curl.exe -sI http://data.sentuor.com/login | Select-Object -First 8

看输出里的 Server: 那一行：

看到的说明 → 去修哪里
Server: nginxnginx 反向代理 → 第 2 步情况 A
Server: Microsoft-IISIIS（可能带 ARR）→ 第 2 步情况 A 里的 IIS 段
Server: uvicorn / python域名直接打到应用（没有反代）→ 第 2 步情况 B
面板类（宝塔 / 1Panel / 花生壳 / frp）面板的反向代理 / 内网穿透 → 第 2 步情况 A 对应段落

拿不准就把这一行输出截图发我。

第 2 步二选一修掉

优先做 A（根治）；A 改不了就做 C（白名单，精确放行，不用重启代理）；只想先登录、别的都不动就做 B（临时关掉兜底）。

情况 A：让代理把原始地址传进去（推荐）

nginx（Windows / Linux 相同）：找到域名对应的 server 块里的 location /，补上两行，别的不动：

location / {
    proxy_pass http://127.0.0.1:8614;
    proxy_http_version 1.1;
    proxy_set_header Host $host;                # ← 这两行是关键
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

保存后：Linux sudo nginx -t && sudo systemctl reload nginx；Windows nginx.exe -t 然后 nginx.exe -s reload。应用不用重启。

IIS + ARR：打开 IIS 管理器 → 点最上面的服务器节点 → 中间找到 Application Request Routing Cache → 右侧 Server Proxy Settings → 勾上 Preserve host header → 应用。然后重启站点（或 iisreset）。

宝塔 / 1Panel 面板：网站 → 你的站 → 反向代理 → 找到这条规则 → 「配置文件」里给 location 加上 proxy_set_header Host $host; 和 proxy_set_header X-Forwarded-Host $host; → 保存并重载。

frp / 花生壳 / 内网穿透：这类最容易把地址换成 127.0.0.1。frp 用 type = http 时默认会透传，如果你配了 host_header_rewrite 就删掉；花生壳找「保留 Host / 透传 Host」开关。找不到就先用情况 B。

情况 C：给应用一个「允许的域名」白名单（精确放行，推荐给反向代理 / 内嵌浏览器场景）

如果代理那边不好改，或者你的浏览器把「来源标记」标成了 same-site，最省事的是告诉应用：来自这个域名的请求是可信的。

# 启动前设置（域名按你的写，是 http 就写 http）
set GATE_ALLOWED_ORIGINS=http://data.sentuor.com

# 多个用逗号分隔：
# set GATE_ALLOWED_ORIGINS=http://data.sentuor.com,http://www.data.sentuor.com

Linux（systemd）：在 [Service] 里加 Environment=GATE_ALLOWED_ORIGINS=http://data.sentuor.com，然后 daemon-reload && restart kb。
Windows（启动窗口 / .bat）：把上面那行 set 加在 python auth_gate\run_gate.py 之前，关掉窗口重开。

安全性：只有「页面来源等于你写的这个域名」的写请求才放行，别的站点照样被挡；比 B（完全关掉兜底）更精确。

情况 B：代理改不了，先临时放行（重启一次应用）

给应用加一个环境变量 GATE_ORIGIN_CHECK=0，它只关掉「老浏览器没有来源标记时」的备用判断；现代浏览器的严格校验仍然生效，登录 Cookie 是 SameSite=Lax，别的站点发起的写请求本来就带不上 Cookie。

Linux（systemd）：

sudo systemctl edit --full kb        # 在 [Service] 里加一行：
Environment=GATE_ORIGIN_CHECK=0
# 保存后：
sudo systemctl daemon-reload && sudo systemctl restart kb

Windows（启动窗口 / .bat）：在启动脚本里 python auth_gate\run_gate.py 那行之前加一行，然后关掉窗口重开：

set GATE_ORIGIN_CHECK=0
提醒：这是临时方案。等代理能传 Host 了（情况 A），把这行删掉、重启一次，恢复完整校验。

第 3 步验证（两条命令 + 一次登录）

在 PowerShell 里执行，两条的输出都应该是 401 或 400（401 = 到了校验账号那一步，正常）：

$u = 'http://data.sentuor.com/__auth/login'
$b = '{"username":"admin","password":"x"}'

function Code($headers) {
  try {
    $r = Invoke-WebRequest -Uri $u -Method Post -ContentType 'application/json' `
         -Body $b -UseBasicParsing -Headers $headers
    [int]$r.StatusCode
  } catch { [int]$_.Exception.Response.StatusCode }
}

# 现代浏览器走这条：期望 401
Code @{ Origin = 'http://data.sentuor.com'; 'Sec-Fetch-Site' = 'same-origin' }

# 老浏览器走这条：修好前是 403，修好后应该是 401
Code @{ Origin = 'http://data.sentuor.com' }

两条都返回 401 → 修好了。然后浏览器 Ctrl+F5 强刷登录页（清掉缓存的旧页面），用真实账号密码登录。

成功的样子：不再出现红字，直接进项目首页（现在是空的，显示「还没有项目 / ＋ 新建项目」）。

说明新版会把「为什么被拒」直接写在红字里

从 2026-11-27 的版本起，这条 403 不再是一句笼统的话，后面会带上实际收到的值，例如：

请求不是本站页面发起的，已拒绝（Sec-Fetch-Site=cross-site（Origin=http://data.sentuor.com，Host=127.0.0.1:8614））
请求不是本站页面发起的，已拒绝（Origin=http://data.sentuor.com 与服务器看到的 Host=127.0.0.1:8614 不一致（X-Forwarded-Host=空））

看到第一句 → 浏览器标的来源不对，用情况 C（白名单）；看到第二句 → 代理没传 Host，用情况 A；服务端日志（journalctl -u kb / 启动窗口）里也会打一行 [gate] 拒绝跨站写请求 …。

需要更新到这一版吗？旧版只说「已拒绝」，没有原因。更新方法：用最新部署包覆盖 auth_gate/gate.py 一个文件，然后重启应用一次。

还不行把这 3 个信息发我

  1. 第 1 步那条命令的完整输出（Server: 那行）
  2. 第 3 步两条命令各自的返回码
  3. 你用的浏览器名字和版本（Chrome 里地址栏输入 chrome://version 第一行）

有这三个我就能定位是「代理没传 Host」还是「浏览器发的来源标记不是同源」，各对应一套确定的改法。

顺便两件安全事

1）现在是 http，密码是明文过网络的。登录通了第一件事：右上角账号菜单 → 改密码。然后尽快上 HTTPS（正式证书 + 应用侧 GATE_HTTPS=1），把访问地址换成 https://。

2）不要把 8614 端口对公网开放。只让代理在本机访问它（应用监听 127.0.0.1），对外只开 80 / 443。

附录这次为什么会突然出现

本机直连时，浏览器地址就是 127.0.0.1:8614，应用看到的也是它，两边一致，所以从来不会触发。挂上域名 + 代理之后，浏览器看到的是 data.sentuor.com，而代理默认会把转发地址换成 127.0.0.1:8614——两边不一致，检查就拒绝了。这也说明安全机制在正常工作，只是代理需要多传一个头。

同样的道理，以后换服务器、换域名、加 CDN / WAF，只要是「前面多了一层转发」，都检查这三件事：Host 传了没、X-Forwarded-Proto 传了没、SSE 有没有被缓冲（实时刷新依赖它）。

IIS 特别提示：IIS 的 ARR 默认会把转发地址改成本机地址，所以用 IIS 做反代时，务必在 Application Request Routing Cache → Server Proxy Settings 里勾上 Preserve host header；否则就依赖上面的情况 C 白名单。
